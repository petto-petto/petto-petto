# 전투 창 초기 렌더링 점검

## 범위 — 2026-09-29

- `work` standard 절차. 기준은 기존 `battle-ui.md`의 화면·조작 규칙이며 신규 기능은 추가하지 않는다.
- 성공 기준: 첫 진입의 불필요한 이미지 준비와 반복 DOM 갱신을 줄이고, 펫 교체·중지·창 크기 변경을 유지한다.
- 수정 범위는 `packages/pet-battle`뿐이다. 공통 앱·IPC·DB, 에셋 원본, 128px 프레임, 발 정렬, 공격 주기·이펙트는 변경하지 않는다.

## 원인 후보와 변경

Explorer에서 확인한 사실:

- 상태 조회마다 배경·펫·적의 같은 `src`를 다시 설정했다. 브라우저가 매번 재디코딩한다는 뜻은 아니지만 이미지 갱신 작업이 반복된다.
- 첫 상태 전에 HTML이 버섯 숲·기본 펫·빨간 적을 먼저 로드했다. 실제 스테이지가 다르면 불필요한 배경을 추가로 읽을 수 있다.
- 첫 관중 DOM 구성 직후 창 크기를 읽고, 같은 HP·스테이지·버튼 텍스트도 반복 생성했다.
- 배경 한 장은 1915×821, RGBA 기준 약 6.29MB다. 최근 발 정렬 계산은 최대 192×48 idle 시트를 URL별 한 번 읽으므로 반복 탐색 병목의 근거가 없다.

Planner / Implementer:

1. 실제 상태의 이미지부터 표시하고 같은 URL·같은 텍스트의 재설정을 생략한다.
2. 현재 펫의 공격 시트만 비동기로 준비해 캐시한다. 준비 완료 콜백은 표시 이미지나 전투 상태를 변경하지 않는다.
3. 관중은 resize에서 계산해 둔 화면 크기를 재사용한다.
4. 실패·늦은 로딩·선택 변경 테스트와 격리된 브라우저 계측으로 확인한다.

## 브라우저 계측

실제 사용자 데이터 없이 새 headless Chrome 프로필, HTTP 데모, 캐시 허용, 640×420 화면의 첫 4초를 측정했다. 변경 전 2회, 변경 후 3회다.

| 항목                      | 변경 전        | 변경 후          |
| ------------------------- | -------------- | ---------------- |
| 배경 / 펫 / 적 `src` 설정 | 50 / 50 / 50회 | 1 / 4 / 1회      |
| 레이아웃 계산             | 52회           | 9~10회           |
| 스타일 재계산             | 244회          | 241~242회        |
| 프레임 간격 p95           | 16.7ms         | 16.7~16.8ms      |
| 32ms 초과 프레임          | 0 / 1회        | 0 / 1 / 0회      |
| 50ms 초과 긴 작업         | 0회            | 0회              |
| 첫 콘텐츠 표시            | 64 / 120ms     | 136 / 96 / 144ms |

주 이미지 설정은 96%, 레이아웃 계산은 약 81~83% 감소했다. 별도로 생성한 이미지 설정은 4→5회로, 공격 시트를 한 번 미리 준비하는 비용이 추가됐다. FPS·첫 표시 시간 개선은 이 결과로 단정하지 않는다. 최초 캐시 비활성 측정은 조건이 달라 비교에서 제외했다.

재실행:

```bash
npm run build --workspace @pet/battle
node packages/pet-battle/test/startup-performance.browser.cjs
```

Chrome 위치는 `BATTLE_BROWSER`로 지정할 수 있다. probe는 전투 정적 파일만 loopback 서버로 제공하며, 사용자 프로필·DB·Electron GUI를 실행하지 않는다. 생성한 브라우저 프로세스와 임시 프로필은 종료 시 정리한다.
