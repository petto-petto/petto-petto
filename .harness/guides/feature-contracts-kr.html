기능 간 계약 규약

각자 자기 feature 패키지 안은 자유롭게 짭니다. 다른 기능과 맞닿는 면만 이 규약을 따릅니다.

규약 네 줄

  1. Port는 생산자가 공표하고 소비자가 가져다 씁니다.
  2. 필요한 계약 목록은 소비자가 요구사항으로 가져옵니다.
  3. 한 쌍 사이에 Port는 한 방향만. 반대 방향은 Event나 주입입니다.
  4. pet-core는 어휘만. 계약을 여기 두지 않습니다.

3번이 1·2번을 지켜 주고, 4번이 3번의 탈출구를 막습니다. 셋째와 넷째가 왜 필요한지는 아래 순환 케이스에서 드러납니다.

소통 창구는 셋입니다

다른 기능에 닿는 방법은 이 셋 중 하나입니다.

창구 성격 컴파일 의존 언제 쓰나
Port 질의 · 명령 — 내가 당겨온다 소비자 → 생산자 지금 값이나 행위가 필요하고, 낡으면 버그일 때
Event 사실 통지 — 발행자는 듣는 사람을 모른다 없음 일어난 일을 알릴 때. 수신자가 0명이어도 정상
주입 값 전달 — 앱이 쥐여준다 없음 받는 쪽이 자기 입력 타입을 선언하고 앱이 채울 때

Event와 주입 구분법 — 문법으로 가릅니다. 과거형 문장으로 쓸 수 있으면 Event입니다(“펫이 진화했다”). 현재 상태 명사면 주입입니다 (“지금 표시 크기”).

의존을 만드는 건 Port 하나뿐입니다. 그래서 순환이 생기면 나머지 둘 중 하나로 바꾸면 풀립니다.

누가 무엇을 소유하나

  • Port — 생산자가 인터페이스와 구현체를 같은 패키지에 둡니다. 소비자는 인터페이스만 import해서 호출합니다.
  • 요구 목록 — 소비자가 가져옵니다. 생산자가 소비자의 필요를 추측하지 않습니다.
  • Event 내용물 — 발행하는 도메인 것입니다. 봉투(이벤트 id, 시각, 스키마 버전)는 어휘라서 pet-core에 둡니다.
  • 주입 타입 — 받는 쪽 것이고, 이름에 남의 도메인이 나오지 않습니다. 다른 기능이 없어도 그 값은 필요하기 때문에 Port가 아닙니다.

한 쌍 사이에 Port는 한 방향만

Port는 곧 의존 화살표입니다. 화살표를 양쪽으로 그릴 수는 없습니다.

어느 쪽이 Port가 되는가 — 행위가 필요한 쪽입니다. 값만 필요한 쪽은 주입받습니다.

양쪽 다 행위가 필요하면 경계가 잘못된 것입니다. 보통 두 기능 사이의 개념 하나가 주인을 못 찾은 상태입니다. 우회하지 말고 그 주인을 정하세요.

그리고 pet-core로 계약을 옮겨 순환을 푸는 것은 금지입니다. 순환 참조는 tsc --build를 실패시키는데, 그 실패가 “이 화살표 하나는 Port가 아니어야 한다”는 신호입니다. core로 옮기면 빌드만 통과하고 결합은 그대로 남습니다.

케이스: 서로가 서로를 필요로 할 때

기능 A는 B의 행위가 필요하고, B는 A가 소유한 값이 필요합니다. 둘 다 Port로 만들면 순환이고 빌드가 실패합니다. A → B만 Port로 둡니다.

생산자 쪽 — 상대 기능의 이름을 모릅니다

// packages/feature-b

// 소비자가 가져다 쓸 계약. 생산자인 여기서 공표한다.
export interface BPort {
  perform(): Result;
}

// B 자신의 입력. 이름에 남의 도메인이 나오지 않는다.
export interface BOptions {
  mode: 'compact' | 'full';
}

export class BService implements BPort {
  #options: BOptions = { mode: 'full' };

  // 앱이 넣어준다. Port 가 아니다.
  applyOptions(options: BOptions): void {
    this.#options = options;
  }

  perform(): Result { /* … */ }
}

앱 — 양쪽을 아는 유일한 곳

// apps/desktop
const b = new BService();
const a = new AService(b);   // A → B 는 Port

const push = () => b.applyOptions({ mode: a.settings().mode });
push();                      // 시작할 때 한 번
a.onSettingsChanged(push);   // 바뀔 때마다
feature-a ──BPort──▶ feature-b feature-b ──────────▶ (없음) ← 순환 없음 apps/desktop ──▶ feature-a ──▶ feature-b ← 앱만 양쪽을 안다

이게 왜 “소비자가 선언”이 아닌가. BPort는 남의 도메인에 대한 계약이라 생산자가 소유합니다. 반면 BOptions는 B 자신의 입력입니다 — A가 없어도 B는 모드가 필요합니다. 나중에 커맨드라인 옵션이 이 값을 채워도 feature-b는 한 줄도 바뀌지 않습니다.

값을 복사해 들고 있기 곤란하면 생성자로 () => BOptions를 주입받으면 됩니다. B는 여전히 feature-a를 import하지 않습니다.

실패는 던지세요

Port는 실패할 때 예외를 던집니다. null이나 0을 돌려주지 않습니다. 0을 받은 소비자는 “데이터가 없음”과 “조회 실패”를 구분할 수 없고, 틀린 값을 그리면서 그것을 알아챌 방법도 없습니다.

이 문서는 사람이 읽는 버전입니다. 에이전트가 따르는 정본은 .harness/rules/feature-contracts.md이며, 규칙이 바뀌면 그쪽을 먼저 고칩니다.
