01 · Command Model

요청 처리와 하네스 진화를 서로 다른 loop로 분리합니다

두 명령이 분리된 이유

work는 한 요청을 안전하게 완료하는 pipeline이고, harness-improve는 반복되는 문제를 다음 작업부터 줄이도록 공통 pipeline 자체를 바꾸는 loop입니다.

요청을 수행할 때

/work · $work

scope와 track을 정하고, 필요한 역할을 통과시켜 fresh evidence로 완료합니다.

공통 flow를 바꿀 때

/harness-improve · $harness-improve

Evidence와 승인을 확보하고, RED/GREEN 계약으로 하네스를 진화시킵니다.

Predictability

과정이 반복됩니다

출력 문장은 달라도 판단과 검증 순서는 같은 흐름을 따릅니다.

Completion Criteria

단계마다 멈춤 조건이 있습니다

Single Source

Claude와 Codex에 같은 지침을 복사하지 않아 런타임별 drift를 막습니다.

02 · Why work Flows This Way

work는 불확실성을 단계별 산출물로 바꿉니다

  1. Entry와 track 선택

    성공 기준과 비목표를 명시하고 feature-spec trigger를 먼저 확인합니다. 범위가 작은 로컬 변경만 lightweight로, 제품 결정이나 넓은 영향이 있으면 standard로 보냅니다.

    writing-great-skills: branch 조건과 completion criterion을 앞에 두어 같은 요청 유형이 같은 process를 타도록 합니다.

  2. Interview / Seed

    standard 기능 작업은 승인된 기획서를 Seed로 사용합니다. 없거나 모호하면 Specifier가 제품의 what/why를 정리하고, 요청자 승인 전에는 다음 역할을 시작하지 않습니다.

    Ouroboros · InterviewOuroboros · Seed
    원리: 제품 결정을 구현 과정에서 암묵적으로 만들지 않도록 입력 계약을 먼저 닫습니다.

  3. Explorer → Planner → Implementer

    Explorer가 사실과 경계를 찾고, Planner가 기술적 how와 검증 계획을 만들며, Implementer가 test-first로 최소 변경을 수행합니다.

    Ouroboros · ExecuteProgressive disclosure
    원리: 역할 계약은 필요한 시점에만 읽혀 정보 계층을 지키고, 탐색·계획·구현의 ownership을 섞지 않습니다.

  4. Verifier → Reviewer

    Verifier는 fresh command output을 얻는 Mechanical과 성공 기준을 대조하는 Semantic을 수행합니다. Reviewer는 구현자 밖에서 회귀·누락·scope drift를 Independent Review합니다.

    Ouroboros · EvaluateMechanicalSemanticIndependent
    원리: 명령 통과와 의미 충족, 독립 검토는 서로 다른 증거이므로 순서대로 모두 기록합니다.

  5. Evolve와 완료 기록

    재사용할 지식이나 반복 friction을 회수하고, 없으면 none을 적습니다. 선택한 track이 요구하는 모든 출력과 남은 gap이 있어야 완료입니다.

    Ouroboros · EvolveObservable completion
    원리: 작업 결과가 다음 실행의 Seed가 되며, 반복 문제는 harness-improve의 Evidence로 넘어갑니다.

03 · Why harness-improve Flows This Way

harness-improve는 한 번의 불편을 근거 있는 공통 변화로 바꿉니다

  1. Evidence를 읽고 재현합니다

    .harness/references/writing-great-skills/SKILL.md와 GLOSSARY.md를 순서대로 읽고, 반복 friction·영향받는 정본·현재 동작·baseline을 수집합니다.

    두 reference의 역할: SKILL.md는 예측 가능한 Skill 저작 원칙을, GLOSSARY.md는 duplication·sediment·no-op 같은 판정 용어를 제공합니다. 둘 다 읽기 전용입니다.

  2. Root cause를 분류하고 Pruning합니다

    누락 지침인지 ownership gap인지, 중복 entrypoint인지, 빠진 검사인지, stale guidance인지 Evidence로 구분합니다. single source of truth를 찾고 중복·침전·no-op을 제거한 가장 작은 변경만 남깁니다.

    writing-great-skills: 새 문장을 추가하는 것보다 기존 정본의 정보 계층과 relevance를 먼저 회복합니다.

  3. 사용자 승인으로 변경 경계를 고정합니다

    Evidence, 원인, pruning 결과, 최소 변경, 영향받는 검사와 완료 기준을 제시합니다. 승인 전에는 공유 하네스 파일을 바꾸지 않습니다.

    원리: 하네스는 다음 팀원의 모든 실행에 영향을 주므로 기술적 가능성만으로 변경 권한을 넓히지 않습니다.

  4. RED → 정본 최소 변경 → GREEN

    원하는 behavior를 검사하는 계약을 먼저 실패시키고, .claude/skills/ 또는 해당 정본 한 곳을 고친 뒤 같은 검사를 통과시킵니다. .agents/skills/는 복사본이 아니라 pointer로 유지합니다.

    원리: 개선이 문구상의 의도가 아니라 관찰 가능한 behavior change임을 증명합니다.

  5. 계약 검증과 기록으로 닫습니다

    bash .harness/tests/verify-contract.sh를 실행하고, .harness/CHANGELOG.md와 friction loop에 scenario·변경 정본·남은 gap·observable completion을 기록합니다.

    Ouroboros · EvolveContract verificationCHANGELOG
    원리: 개선 결과가 다음 work 실행에서 재사용되며 loop가 닫힙니다.

04 · One Flow, Two Runtimes

두 런타임은 복사본이 아니라 하나의 정본을 공유합니다

Claude Code · CLAUDE.md
Codex · .agents/skills/
→
공통 정본

AGENTS.md · .claude/skills/ · .harness/

  • CLAUDE.md는 AGENTS.md만 import합니다.
  • Claude Code 정본 Skill은 .claude/skills/work/와 .claude/skills/harness-improve/에 있습니다.
  • Codex의 .agents/skills/work와 .agents/skills/harness-improve는 해당 정본을 가리키는 상대 어댑터입니다.
  • 역할, 규칙, reference, 계약 검증은 .harness/에서 함께 관리합니다.

따라서 Claude Code의 /work와 Codex의 $work는 호출 문법만 다를 뿐 같은 track·역할·검증 pipeline을 읽습니다. harness-improve도 동일합니다.

05 · Boundaries

차용한 원리와 실제 증거의 범위를 구분합니다

Concept Boundary

Ouroboros는 실행하지 않습니다

Interview·Seed·Execute·Evaluate·Evolve라는 개념만 기존 pipeline을 설명하는 데 사용합니다. 외부 도구를 설치하거나 모델 호출을 자동화하지 않습니다.

Reference Boundary

writing-great-skills는 읽기 전용입니다

두 embedded reference는 하네스 작성과 pruning의 판단 기준이며 수정 대상이나 실행 엔진이 아닙니다.

검증 증거가 보장하지 않는 것

fixture는 보존된 출력이지 live agent invocation이 아니므로 모든 프롬프트에서 같은 행동을 보장하지 않습니다. 정적 계약은 구조와 기록된 규칙을 증명하지만, Rust 동작은 manifest가 준비된 상태에서 .harness/scripts/verify-rust.sh를 실제 실행해야 증명됩니다.

팀원이 실행하는 것은 work와 harness-improve이며, 개념과 역할은 그 두 pipeline 안에서 필요한 시점에 작동합니다.
