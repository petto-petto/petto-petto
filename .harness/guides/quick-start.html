02 · work Pipeline

work는 먼저 일을 분류한 뒤, 필요한 깊이만큼 실행합니다

/work 또는 $work

요청과 성공 기준을 받은 뒤 Entry → track 선택 → 실행 → 검증 → 완료 기록 순서로 진행합니다.

요청·성공 기준→Entry 판단→lightweight / standard→fresh 검증→완료 기록

03 · work Entry

track보다 먼저 feature-spec trigger를 확인합니다

사용자에게 보이는 새 동작이나 변경, 도메인 규칙, 공개 인터페이스, 저장 형식, 모호한 기능 요청 중 하나라도 해당하면 standard를 선택합니다. 의존성 작업도 standard입니다. 그 외에 범위가 작고 이미 이해된 로컬 변경만 lightweight를 선택할 수 있습니다.

lightweight

경계와 성공 기준이 이미 분명한 작은 로컬 변경을 빠르게 검증합니다.

standard

제품 결정, 여러 경로, 의존성 또는 넓은 검증이 필요한 작업을 역할별로 분리합니다.

기획서가 없다는 사실만으로 gate를 넓히지 않습니다

먼저 trigger가 적용되어 standard로 들어온 기능 작업인지 확인합니다. 그 다음에만 승인된 기능 기획서를 찾고, 없거나 모호하면 조건부 Specifier를 실행합니다.

04 · work / Lightweight

작은 변경은 네 단계의 짧은 loop로 끝냅니다

  1. Scope confirmation

    영향받는 동작, 변경 경계, 성공 기준을 먼저 고정합니다.

    원리: 작은 작업도 경계가 없으면 scope drift가 생기므로 완료 조건부터 선명하게 만듭니다.

  2. Minimal implementation

    범위 안에서 가장 작은 변경을 수행하고, 동작 변경이면 집중 테스트를 먼저 실패시킵니다.

    원리: Implementer 역할을 따로 호출하지 않더라도 test-first와 최소 변경 원칙은 유지합니다.

  3. Mechanical verification

    적용 가능한 formatter·build·lint·test를 마지막 변경 뒤 새로 실행합니다.

    Rust: manifest가 준비되어 있으면 bash .harness/scripts/verify-rust.sh가 공용 완료 게이트입니다.

  4. Diff review

    변경 파일을 다시 보고 범위 이탈, 의도하지 않은 편집, 남은 gap을 기록합니다.

    원리: lightweight는 역할 수를 줄이지 증거를 생략하지 않습니다.

05 · work / Standard

제품 결정부터 독립 검토까지 역할을 분리해 흘려보냅니다

  1. Interview / Seed

    가정, 성공 기준, 비목표, 미해결 결정을 정리합니다. feature-spec trigger로 들어온 작업은 승인된 기획서를 Seed로 사용합니다.

    Specifier가 붙는 때: 기획서가 없거나 모호할 때만 제품의 what/why를 Draft로 만들고 요청자 승인을 기다립니다. 승인 전에는 뒤의 다섯 역할이 막힙니다.

  2. Explore and plan

    Explorer가 호출 경로·데이터 경계·기존 패턴과 최소 변경 면을 찾고, Planner가 이를 테스트 가능한 순서와 검증 명령으로 바꿉니다.

    역할을 나누는 이유: 사실 탐색과 기술적 how 결정을 분리해 추측이 계획으로 굳는 것을 막습니다.

  3. Implement

    Implementer가 concern 하나씩 집중 테스트를 RED로 만든 뒤 최소 구현으로 GREEN을 만듭니다.

    완료 경계: Implementer는 구현 증거를 만들지만 전체 완료를 선언하지 않습니다.

  4. Verify and review

    Verifier가 Mechanical과 Semantic을 수행하고, Reviewer가 구현자 밖에서 Independent Review를 수행합니다.

    Mechanical→Semantic→Independent Review
    순서의 의미: 명령 성공, 성공 기준 충족, 회귀·누락 검토는 서로 다른 질문이므로 한 결과로 뭉치지 않습니다.

  5. Evolve

    재사용할 지식이나 반복 friction을 회수하고, 없으면 none을 명시합니다.

    원리: 한 번의 작업에서 얻은 교훈이 다음 실행의 Seed 또는 하네스 개선 Evidence가 됩니다.
Explorer→ Planner→ Implementer→ Verifier→ Reviewer

06 · work Completion

pipeline의 각 출력을 기록해야 완료입니다

lightweight는 track·scope·집중 증거·fresh Mechanical 결과·diff review·변경 파일·남은 gap을 기록합니다. standard는 여기에 Interview/Seed, 다섯 역할 출력, 세 검토 결과, Evolve disposition을 더 기록합니다.

fresh output이 없으면 완료가 아닙니다

필수 검사가 막히거나 실패하면 blocker와 남은 gap을 보고합니다. 이전 실행 결과나 정적 설명만으로 통과했다고 표현하지 않습니다.

07 · harness-improve Pipeline

harness-improve는 Evidence가 승인된 변경으로 진화하는 loop입니다

/harness-improve 또는 $harness-improve

공유 하네스는 팀 전체의 다음 실행을 바꾸므로, 추측으로 규칙을 추가하지 않고 Evidence → 승인 → RED/GREEN → 계약 완료를 강제합니다.

  1. Read evidence → Evidence → Root cause

    writing-great-skills/SKILL.md와 GLOSSARY.md를 순서대로 읽고, 정확한 요청·반복 friction·영향받는 정본·재현 가능한 baseline을 모읍니다. 그 뒤 누락 지침, ownership gap, 중복 entrypoint, 빠진 검사, stale guidance 중 실제 원인을 분류합니다.

    요소의 역할: embedded reference는 규칙을 더 쓰기 위한 재료가 아니라 Evidence를 판정하고 정본을 찾는 기준입니다.

  2. Pruning and smallest change → User approval

    single source of truth를 찾고 duplication·sediment·no-op을 먼저 제거합니다. 관찰 가능한 행동을 바꾸는 가장 작은 안, 영향받는 검사, 완료 기준을 제시하고 명시적 승인을 받습니다.

    승인 전 경계: 파일은 바꾸지 않습니다. 읽기 전용 결과에는 RED 이후 단계가 “다음 계획”으로만 기록됩니다.

  3. RED → smallest canonical change → GREEN

    승인된 동작을 검사하는 실행 가능한 계약 또는 behavior check를 먼저 추가해 예상 실패를 기록합니다. 그 다음 정본 한 곳만 최소 수정하고 같은 검사를 통과시킵니다.

    어댑터 원리: Claude/Codex별 지침을 복제하지 않고 .agents/skills/는 .claude/skills/ 정본을 가리키는 pointer로 유지합니다.

  4. Contract verification → CHANGELOG → Observable completion

    bash .harness/tests/verify-contract.sh를 마지막 변경 뒤 실행하고, .harness/CHANGELOG.md와 friction loop에 scenario·정본 변경·남은 gap·결과를 기록합니다.

    완료 경계: 필요한 check가 막히거나 실패하면 완료를 선언하지 않습니다. fixture는 보존된 증거이지 모든 live agent 동작의 보편적 보장이 아닙니다.

실행 진입점은 work와 harness-improve입니다. 이 HTML은 팀 설명용이며 실제 완료 조건은 저장소 정본 계약이 소유합니다.
