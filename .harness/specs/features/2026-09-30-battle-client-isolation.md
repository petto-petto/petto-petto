# Feature specification: 전투 연동의 Client 경계와 공통 영향 축소

## Status

Approved — 2026-09-30 요청자의 “다 진행한 뒤 mr 리팩토링 진행”으로 승인됐습니다.
설계 승인 상태이며 구현·검증 완료를 의미하지는 않습니다.
2026-10-01 요청자의 “이전의 펫룸 저장 연결 코드는 … 내쪽에서 추가한건지? 그럼 삭제해”가
펫룸 저장 연결 범위를 대체합니다. 아래는 해당 삭제 지시를 반영한 기준이며 별도 reader Draft 전체 승인이 아닙니다.

후속 “전투창. 메인 오버레이는 ㄴㄴ” 요청의 선택 읽기 복구 범위는
[승인된 reader 명세](./2026-09-30-battle-active-pet-reader.md)를 따릅니다.
룸 저장 제거는 유지하고, 아래 선택 전달 규칙은 이 후속 명세로 갱신했습니다.

## Owner

요청자: 전투 담당자(srkim0917)입니다. 펫룸의 공개 화면 계약은 펫룸 소유 영역이며,
공통 펫 데이터 계약은 기존 `@pet/client`의 `PetClient`를 그대로 사용합니다.

## Problem and user outcome

전투 MR의 공통 변경 중 펫룸 선택, 앱 시작·종료, 오버레이 이미지 로딩, 루트 Rust 빌드는
다른 담당자의 기능에 영향을 줍니다. 이를 Client/Adapter 경계로 줄이되, 사용자가 현재
사용하는 전투 선택·XP 반영·실제 에셋·모션·창 기능은 빠지지 않아야 합니다.

출발점은 `30c235d`의 [MR §2](../../../packages/pet-battle/docs/2026-09-30-battle-mr.md)와
[교차 기능 점검](../../../packages/pet-battle/docs/2026-09-30-rebase-impact-audit.md)입니다.
단순히 파일을 전투 폴더로 이동하거나 인터페이스 이름만 추가하는 작업은 목표가 아닙니다.

## Scope

| 현재 영향 항목 | 제안하는 책임 경계 | 남겨야 하는 연결 |
| --- | --- | --- |
| 앱 `main.ts`의 전투 조립·종료 | 전투 소유 Client와 런타임 수명 처리는 `packages/pet-battle`이 담당합니다. | 앱은 공통 PetClient·성장 곡선·에셋 위치·신뢰할 전투창과 종료 신호만 제공합니다. |
| 앱 `room.ts`·`collection.ts`의 펫룸 연결 | 전투 브랜치가 추가한 Client 주입·조회/저장 분기를 제거해 원격 main과 같게 합니다. | 펫룸은 원래 JSON 저장을 유지합니다. 조회 전용 Adapter만 전투에 주입합니다. |
| 루트 `package.json`의 전투 Rust 빌드 | 개발용 Rust 준비와 실행은 전투 패키지의 책임으로 옮깁니다. 다른 창의 실행을 전투 빌드가 막지 않게 합니다. | 첫 전투 요청은 준비 완료를 기다린 뒤 처리합니다. 데모·명시적 전투 빌드 경로는 유지합니다. |
| 공통 오버레이 `PetSprite.jsx`의 지연 이미지 방지 | 오버레이 자체의 수정이므로 기존 2줄 가드를 유지합니다. 전투는 이미 보유한 독립 이미지 가드를 유지합니다. | 오버레이가 전투 패키지에 의존하도록 바꾸지 않습니다. 외부 순변경 0건으로 표시하지 않습니다. |
| 전투창 크기·preload | 기존 전투 패키지 옵션과 전용 preload를 유지합니다. | 실제 BrowserWindow 생성은 앱 소유이므로 최소 호스트 연결은 유지합니다. |

## Non-goals

- 공통 DB·migration·PetClient 소유 구현 변경, 펫 DB 복제, 원시 SQL 접근은 하지 않습니다.
- 전투에서 토큰을 XP로 환산하거나 펫 성장·선택 정보를 대신 기록하지 않습니다.
- 펫룸·오버레이를 전투 패키지에 숨겨 넣거나, 종 이름으로 보유 개체를 추측 연결하지 않습니다.
- 이미 확인된 `pet_profiles`와 `owned_pets`의 성장 통합은 별도 소유자 작업입니다.
- 열린 펫룸에 뽑기·합성 결과를 실시간 push하는 새 기능은 포함하지 않습니다. 기존 재조회
  결과는 보존하며, 이 한계를 Client 이전만으로 해결했다고 주장하지 않습니다.
- 전투 디자인·크기·밸런스·모션 규칙을 바꾸지 않습니다.
- 다른 원격 feature를 병합하거나 push·강제 push하지 않습니다.

## Domain rules

1. 공통 펫 데이터의 계약은 **기존 PetClient 하나**입니다. `RoomPetReadClient`는 그 조회
   메서드의 부분집합이며 Adapter에 선택·성장 저장 메서드를 노출하지 않습니다. 새 Repository는 없습니다.
2. 전투는 공통 보유 개체 ID로 같은 종 두 마리를 구별합니다. 기존 JSON 시드 ID와 UUID를
   종·이름으로 추측 대응하지 않습니다.
3. 전투는 공통 저장소의 확정된 누적 XP를 읽습니다. 공격 모션이 XP·재화를 쓰지 않습니다.
4. 현재 앱은 룸 선택 Client를 전투에 주입해 JSON의 현재 선택을 읽습니다.
   정확히 같은 개체만 공통 저장 XP를 연결하고, 미연결 펫도 외형·모션을 표시하되 XP는 만들지 않습니다.
   선택 Client를 생략한 기존 소비자는 공통 활성값을 그대로 따릅니다.
   원래 JSON 저장·legacy 조회는 보존하고 전투가 이를 대체하거나 XP를 계산해 기록하지 않습니다.
5. 다른 기능의 의미를 바꾸지 않기 위해 공통 오버레이 이미지 경합 방지 수정은 제거하지 않습니다.
6. 전투 런타임 준비는 승인된 전투 요청에서만 시작하며 동시 요청은 준비 작업 하나를
   공유합니다. 닫기·종료 이후 늦게 준비가 끝나도 자식 프로세스를 다시 만들지 않습니다.
7. 개발 준비 실패는 전투 화면에 표시하고 재시도할 수 있어야 합니다. 실패한 요청을
   성공이나 빈 펫 목록으로 바꾸지 않습니다. 배포용 명시 바이너리는 자동 빌드하지 않습니다.

## Acceptance criteria

| 보존·개선 기준 | 검증 방법 |
| --- | --- |
| 공통 PetClient 선택 → 조회 Adapter → 전투의 개체·등급·레벨·진화·에셋이 같습니다. | 실제 임시 SQLite + 실제 Rust 통합 검증입니다. |
| 같은 종의 다른 보유 개체, 선택 해제, 명부 비어 있음, 재시작을 정확히 구분합니다. | 펫룸 Client 및 전투 연동 계약 테스트입니다. |
| 기존 펫룸 선택·JSON 저장·legacy 조회는 원래대로이며 공통 활성 펫을 변경하지 않습니다. | main 대비 두 파일 순차이 없음 + JSON/SQLite 분리 회귀입니다. |
| XP 증가에 따른 부드러운 HP 감소·정복·다음 적·투명도 보존이 유지됩니다. | 기존 실제 Rust 연동·전투 규칙 테스트입니다. |
| 공격·두더지 모션·STOP/START·카메라·위치 유지·크기 조절·닫기가 유지됩니다. | 기존 UI 계약 테스트 및 격리 Electron 회귀 검증입니다. |
| 루트 앱 빌드가 전투 Rust 빌드에 의존하지 않습니다. | 루트 스크립트 계약과 Cargo 없는 환경을 격리한 시작 경로 검증입니다. |
| 준비 중 동시 요청·실패·재시도·종료를 안전하게 처리합니다. | 실행기를 주입한 단위 테스트와 실제 개발 바이너리 통합 검증입니다. |
| 뽑기·합성은 기존 명부·재화·활성 보호를 유지합니다. | 기존 호스트 거래 테스트를 재실행합니다. |
| 외부 변경은 설계한 소유자 Client·호스트 조립·검증에 한정됩니다. | 최종 main 대비 diff와 MR §2의 현재 영향 표로 확인합니다. |

## Edge and error cases

- 펫 조회 실패를 활성 없음으로 숨기지 않습니다. 선택 실패 시 이전 활성 펫은 보존합니다.
- 알 수 없는 에셋·진화 단계·중복 종을 다른 펫으로 대체하지 않습니다.
- 첫 전투 실행의 비동기 준비가 기존 IPC 응답 기한을 넘을 때 무한 대기하거나 중복 실행하지 않습니다.
- Rust 미설치·빌드 실패·실행 파일 누락·실행 중 종료를 구분합니다. 사용자 요청에 따른
  재시도 경로와 준비 취소 시 정리 범위를 테스트해야 합니다.
- 실제 사용자 DB·사용량 수집을 검증에 사용하지 않습니다.

## API and data impact

기존 BattleClient의 화면 명령·응답 및 PetClient의 데이터 계약은 유지합니다.
기존 `createBattleRuntime()`의 동기 카탈로그 검증·오류 전파도 유지합니다. 비동기 준비는
전투 기동 연결 단계에서 처리하며 기존 팩터리의 의미를 조용히 바꾸지 않습니다.
읽기 전용 Client/Adapter와 전투의 런타임 준비·수명 연결 계약이 변경 대상입니다.
이전 펫룸 UI Client와 선택 저장 연결은 삭제합니다.
저장 형식이나 DB 테이블을 추가하지 않습니다. 기존 오버레이·공통 성장의 미연동을 이번
리팩토링으로 해결한 것처럼 주장하지 않습니다.

## Open questions

요청자가 아래 설계 범위를 승인했습니다.

- 2026-10-01 삭제 지시에 따라 펫룸 저장 주입은 제거합니다. `packages/pet-room`의
  읽기 전용 Client/Adapter만 전투에서 사용하며 기존 JSON→공통 선택 저장은 남기지 않습니다.
  후속 reader 명세에 따라 룸 선택을 전투에 읽어오는 연결은 추가합니다. 메인 오버레이는 변경하지 않습니다.
- 오버레이 자체의 2줄 버그 수정은 그대로 유지합니다. 그 변경까지 이번 MR에서 제거하려면
  별도 소유자 패치로 분리하는 결정을 먼저 받아야 합니다.

미결정 제품 범위는 없습니다. `work standard`의 승인된 Seed로 사용합니다.
