# Feature specification: AI 도구 토큰 사용량

This specification owns the product what and why. The related implementation
plan owns the technical how.

## Status

Approved

## Owner

cksgud410

## Problem and user outcome

AI 도구(Claude Code·Codex·Gemini CLI)의 토큰 사용량이 저장소에 없다. 현재는 meta의
`meta-state.json` 한 덩어리에 들어 있고, meta 소유이며, 파일 전체를 읽고 쓰는 구조라
다른 기능이 조회할 수 없다.

그 결과 "어느 도구로 토큰을 얼마나 썼는가"에 답할 수 있는 공통 경로가 없다. 재화 환산의
입력값도 집계 반환값으로 흘러 지나갈 뿐 남지 않는다.

사용자 관점의 결과: 도구별 사용량을 화면에 보여줄 수 있고, 앱을 껐다 켜도 남으며, 같은
사용 기록이 두 번 반영되지 않는다.

## Scope

- 도구별 토큰 사용량을 공용 `petto.sqlite`에 저장한다.
- 적재, 도구별 조회, 전체 조회, 최근 내역 조회를 공통 인터페이스로 제공한다.
- 같은 인입이 두 번 도착해도 사용량이 두 배가 되지 않는다.
- 소비 기능이 SQLite·Electron을 모르고 쓸 수 있어야 한다.

## Non-goals

- **재화 전부** — 잔액, 차감, 음수 방지 제약, 토큰→코인 환산 비율. 재화 도메인 소유다.
- **인입 경로 연결** — hook이든 주기 집계든 `recordUsage()`를 호출하는 코드는 붙이지
  않는다. `main.ts`를 수정하지 않는다.
- **모델별 분해** — `claude-opus-5` 단위 집계. 현재 집계 반환값에 분해가 없어 meta
  파이프라인 수정이 필요하다.
- **기존 `meta-state.json` 사용량의 자동 이관.**
- meta 패키지 수정.

## Domain rules

- **사용량은 누적만 한다.** 차감 연산이 존재하지 않는다. 이미 발생한 사용은 사실이며,
  무언가를 소비했다고 줄어들지 않는다. 줄이면 사용량 화면과 누적 기반 업적이 함께 틀어진다.
- **모든 수량은 0 이상의 안전한 정수다.** 음수가 구조적으로 불가능하다.
- **관측 토큰과 보상 대상 토큰을 분리해서 저장한다.** 전자는 캐시 읽기를 포함한 표시용,
  후자는 재화 환산 대상이다. 하나로 합치면 다른 쪽을 복원할 수 없다.
- **중복 판정은 데이터베이스가 한다.** 호출자가 넘긴 멱등 키에 `UNIQUE`를 걸어 판정하며,
  응용 코드의 조회-후-삽입에 맡기지 않는다. 두 문장 사이에 끼어든 두 번째 인입을 막지
  못하기 때문이다.
- **멱등 키의 형식은 호출자가 정한다.** 무엇이 유일한지는 인입 경로만 안다.
- **통계와 내역은 언제나 일치한다.** 도구별 통계 값은 같은 도구의 내역 합과 같다. 둘은
  한 트랜잭션에서만 함께 바뀐다.

## Acceptance criteria

| 관측 가능한 결과 | 확인 방법 |
| --- | --- |
| 적재하면 통계와 내역이 함께 생긴다 | 통합 테스트 — 적재 후 두 테이블 모두 조회 |
| 같은 멱등 키 재적재가 아무것도 바꾸지 않고 `false`를 돌려준다 | 통합 테스트 — 누적·행 수·기록 시각 불변 |
| 도구마다 통계 행이 따로 쌓이고, 기록 없는 도구는 행이 없다 | 통합 테스트 — 두 도구 적재 후 목록 비교 |
| 닫고 다시 열어도 통계·내역·멱등 키가 남는다 | 통합 테스트 — 재연결 후 조회 |
| 잘못된 입력을 거부하고 아무것도 남기지 않는다 | 통합 테스트 — 5종 입력 거부 후 빈 상태 확인 |
| 적재 중 실패하면 통계와 내역이 함께 rollback된다 | 통합 테스트 — 통계 CHECK 위반 유발 후 두 테이블 확인 |
| 늦게 도착한 과거 인입이 마지막 기록 시각을 되돌리지 않는다 | 통합 테스트 — 10시 → 9시 순 적재 후 시각·누적 확인 |
| 멱등 키의 앞뒤 공백 차이로 중복이 통과하지 않는다 | 통합 테스트 — 공백 포함 키와 미포함 키 연속 적재 |
| migration이 재실행 시 중복 적용되지 않는다 | 통합 테스트 — 재연결 후 `schema_migrations` 확인 |
| 기존 기능 테이블과 같은 파일에 공존한다 | 통합 테스트 — scope 목록 확인 |

## Edge and error cases

- 알 수 없는 도구 식별자 → 예외.
- 음수·소수·JS 안전 정수를 넘는 토큰 수 → 예외. `better-sqlite3`가 안전 정수 초과 값을
  거부하지 않고 조용히 받으므로, 응용 검증과 DB `CHECK` 상한을 모두 건다.
- 빈 멱등 키(공백만 포함), 빈 발생 시각 → 예외. 멱등 키는 앞뒤 공백을 제거해 저장하므로
  공백 차이만으로 다른 키가 되지 않는다.
- 기록이 없는 상태의 조회 → `[]` 또는 `{ observed: 0, reward: 0 }`. 예외가 아니다.
- 적재 도중 실패 → 두 테이블 모두 rollback. 한쪽만 반영된 상태는 존재하지 않는다.

## API and data impact

**신규 테이블** — `token` migration scope version 1

| 테이블 | 내용 |
| --- | --- |
| `token_stats` | 도구마다 한 행. 관측·보상 누적, 마지막 기록 시각 |
| `token_history` | 적재 한 건. 도구, 관측·보상 토큰, 멱등 키(`UNIQUE`), 발생 시각 |

**기존 패키지 확장** — `@pet/client`에 `packages/pet-client/src/token.ts`를 추가하고
`TokenClient`, `UsageEntry`, `ProviderTokenStats`, `TokenTotals`, `TokenHistoryEntry`를
re-export한다. 클라이언트 인터페이스를 한 패키지에 모아 둔다.

기존 테이블·패키지 변경 없음. 호환성 영향 없음 — 새 scope라 기존 DB는 다음 실행에서
테이블만 추가된다.
