# Feature specification: 뽑기·합성의 펫·재화 연결

## Status

Approved (요청자 승인, 2026-09-28)

## Owner

동우 (요청자)

## Problem and user outcome

뽑기 결과는 현재 실제 보유 펫으로 저장되지만 비용은 화면의 임시 잔액에서만 빠진다.
합성은 펫 목록과 잔액이 모두 임시 데이터라 뽑은 펫을 재료로 쓸 수 없다. 사용자는
공유 잔액으로 뽑기와 합성을 하고, 결과·재료·비용이 앱 재시작 후에도 일치하기를 원한다.

## Scope

- 뽑기 1회 비용 100,000, 10회 비용 1,000,000을 공유 재화 잔액에서 차감한다.
- 뽑기 후보는 실제 펫 종류 목록을 사용하고 결과 개체를 기존 `PetClient`에 저장한다.
- 합성 화면은 실제 보유 개체와 펫 종류를 읽는다. 재료 선택은 종이 아닌 개체 단위다.
- COMMON 10개체는 비용 30,000으로 RARE 1개체, RARE 10개체는 비용 100,000으로
  EPIC 1개체를 만든다. 기존 균등 결과 추첨 규칙을 유지한다.
- 뽑기와 합성은 `TokenClient`의 저장된 재화 잔액을 조회·차감한다.
- 화면의 Token 1은 현재 재화 원장의 Coin 1과 같은 단위다.
- 새 저장소는 재화 0으로 시작한다. 테스트용 재화는 관리자 명령으로 원하는 금액을 지급한다.
- 한 요청의 재화 차감과 펫 생성·교체는 함께 성공하거나 함께 취소된다.
- 성공·실패 후 화면은 실제 보유 개체 및 잔액으로 갱신된다.

## Non-goals

- AI 도구 사용량 누적 사실 자체의 차감. 사용량 통계는 소비 후에도 유지한다.
- 서버 동기화, 펫 종류 카탈로그 편집, 합성 성공 확률 또는 EPIC 상위 등급 추가.
- 뽑기 천장 상태의 앱 재시작 간 영속화.
- 운영 지급 정책을 확정하는 일.

## Domain rules

1. 재화가 부족하면 뽑거나 합성할 수 없고 펫·재화·뽑기 천장 상태는 변하지 않는다.
2. 합성 재료는 서로 다른 보유 개체 ID 10개이며 선택한 탭의 등급과 일치해야 한다.
3. 활성 펫은 합성 재료로 사용할 수 없다.
4. 결과 종류는 목표 등급의 실제 카탈로그에서 균등하게 선택한다.
5. 성공 결과는 새 개체이며 레벨 1, XP 0, 진화 단계 0, 비활성 상태다.
6. 저장 실패가 어느 단계에서 나도 펫과 재화 변경 전체를 되돌린다.
7. 재화는 음수가 될 수 없다. 중복 요청은 같은 요청으로 두 번 차감하지 않는다.
8. 앱 시작은 재화를 자동으로 지급하지 않는다. 기존 원장 잔액은 그대로 유지한다.

## Acceptance criteria

- 뽑기·합성 창을 함께 열면 같은 저장 잔액을 표시한다. 한 창의 소비 뒤 다른 창의 다음
  조회·요청은 갱신된 잔액을 사용한다.
- 뽑기로 얻은 개체가 합성 재료 목록에 나타난다. 합성 성공 시 정확히 선택한 10개체가
  사라지고 새 결과 1개체가 남는다. 앱 재실행 후에도 이 결과가 유지된다.
- 부족한 재화, 부족하거나 잘못된 재료, 빈 결과 후보, DB 저장 오류는 명확한 메시지를
  보이고 펫과 잔액을 변경하지 않는다.
- 펫 저장 실패 뒤에도 비용이 남고, 재화 차감 실패 뒤에도 펫 변경이 없다.
- 1회·10회 뽑기 및 COMMON·RARE 합성의 비용과 결과를 실제 임시 SQLite 파일에서 검증한다.
- 새 저장소의 재화 잔액은 0이며 재시작해도 자동 지급이 없다. 관리자 명령으로 지급한
  금액은 기존 원장에 더해지고 재시작 후에도 유지된다.

## Edge and error cases

- 앱 시작 시 재료가 10개 미만이면 선택 가능한 개체만 표시하고 합성 시 재료 부족을 알린다.
- 같은 종류의 펫을 여러 마리 보유해도 각 개체를 따로 선택·소비한다.
- 성공 직전 잔액이나 보유 펫이 다른 창에서 변경되면 최신 저장 상태를 다시 검증한다.
- 실패 응답이나 중복 클릭은 결과 연출을 시작하지 않고 재시도 가능 상태로 되돌린다.

## API and data impact

- 기존 `TokenClient` 계약에 재화 잔액 조회, 지급, 부족액 거부, 소비 기록을 추가한다.
- 별도 `CurrencyClient`는 만들지 않는다. 사용량 통계와 소비 가능한 원장은 구분해 유지한다.
- `PetClient`의 기존 조회·생성·교체 기능은 활용하며 필요한 계약 변경만 추가한다.
- 공통 `petto.sqlite`의 트랜잭션 경계가 두 소유 영역의 쓰기를 감싼다.
- 기존 저장 데이터를 파괴하거나 데모 잔액을 실제 잔액으로 이관하지 않는다.
